Internal Playbook · v1.0

Using Devin for End-to-End Software Delivery in a Tier-1 Bank

A practical playbook for Knowledge, Playbooks, and governance — from Product Owner requirements through development, bug fixing, and production support — for backend services (Java/Spring, Python) integrated with Jira, Bitbucket/GitHub, Jenkins, and ServiceNow.

1. The mental model

Devin gives you three primitives that matter for an enterprise rollout:

  • Knowledge — persistent facts Devin retrieves contextually.
  • Playbooks — parameterized procedures Devin executes.
  • Sessions — actual runs, triggerable from Jira, Slack, API, or webhooks.

Everything else (repo setup, secrets, machine config, integrations) is plumbing in service of those three. In a tier-1 bank you also need a fourth column running alongside:

  • Guardrails — what Devin is not allowed to do, encoded both in policy and in the sandbox's network/permission boundary.
Reframe: Treat Devin as a junior engineer with infinite stamina, perfect recall of your standards (if you write them down), and zero judgment about your business. Knowledge and Playbooks are how you compensate for that last part.

2. Mapping Devin to the SDLC

2.1 PO raises requirements

Don't have Devin write code from a PO's first-draft story. Have it refine the story.

A Story Refinement playbook takes a Jira ticket and produces:

  • Impacted services and repos (from a codebase scan)
  • Proposed implementation approach
  • Open questions for the PO
  • Suggested acceptance criteria
  • Suggested test scenarios (happy path, edge cases, negative)
  • Rough effort signal (S / M / L)

The PO and tech lead close out ambiguity before any code is touched. This single change usually pays for the rollout — your Definition of Ready becomes machine-enforced.

2.2 Development

Once a story is Ready for Dev, a Jira webhook (on status transition) triggers Devin via an Implement Story playbook. The playbook:

  1. Checks out a feature branch using your naming convention (e.g. feature/PAY-1234-add-idempotency).
  2. Implements against the acceptance criteria.
  3. Writes unit and integration tests.
  4. Runs the local pipeline (SonarQube, Checkmarx, OWASP dependency check).
  5. Opens a PR populated from your standard PR template (linked Jira, risk class, test evidence, rollback note).

Critical: Devin is only the author. Segregation of duties means a human approver and the existing CI gates remain mandatory. Devin's PRs must be visually marked (a label, a bot identity) so reviewers know what they're reading.

2.3 Bug fixing

This is where Devin gets very good very quickly because the loop is tight.

A Triage & Fix Defect playbook:

  1. Reads the Jira defect or ServiceNow incident.
  2. Attempts to reproduce in dev.
  3. Writes a failing test that captures the bug.
  4. Fixes the bug.
  5. Raises a PR linked to the defect ID.

The "failing test first" discipline is enforceable through the playbook — much easier than enforcing it through code review.

2.4 Production support

In a tier-1 bank, Devin should have no write access to production. Period.

What Devin can do is investigate. A Prod Incident Investigation playbook:

  1. Pulls approved log/metric slices via your observability stack.
  2. Summarises what it found.
  3. Proposes a hypothesis and a blast-radius estimate.
  4. Drafts a hotfix PR against the dev branch for human review.
  5. Drafts an RCA skeleton and posts it to the ServiceNow incident.

The human always commands the deploy. Devin never bypasses change management.

3. Knowledge architecture

Treat Knowledge like a curated library, not a wiki.

3.1 Three rules

  1. Tier by scope. Global → Domain → Repo → Service. Devin retrieves contextually, but you control scope via repo configuration.
  2. Categorize consistently. Standards, Patterns, Architecture, Tools, Pitfalls, Glossary. One category per entry.
  3. One assertion per entry. Long entries do not retrieve well.

3.4 Maintenance

  • Assign an owner per domain.
  • Run a quarterly review: prune stale entries, merge duplicates, flag contradictions with current code.
  • Drift is the silent killer. Treat Knowledge like production config.

4. Playbook architecture

A two-layer design works best.

4.1 Atomic playbooks (single-purpose, parameterised)

  • pr.open-from-template — open a PR using the house template.
  • scan.security-suite — run SonarQube + Checkmarx + OWASP DC, attach results to PR.
  • tests.generate-data — generate fixture data conforming to a schema.
  • jira.post-progress — append progress summary to a Jira ticket.
  • slack.notify-channel — post status to a Slack channel.

4.2 Composite playbooks (chain atomics for an SDLC stage)

  • story.refine — Story Refinement (see §2.1).
  • story.implement — Implement Story (see §2.2).
  • defect.triage-and-fix — Triage & Fix Defect (see §2.3).
  • incident.investigate — Prod Incident Investigation (see §2.4).
  • deps.upgrade — Dependency upgrade (CVE-driven or scheduled).
  • debt.refactor — Tech-debt refactor against a specific Knowledge entry.

4.4 A sample playbook spec

name: story.implement
inputs:
  jira_ticket_id: string (required)
  target_branch: string (default: develop)
preconditions:
  - Ticket status must be "Ready for Dev"
  - Ticket must have acceptance criteria populated
  - Ticket must be linked to a single component (repo)
steps:
  1. jira.fetch_ticket(jira_ticket_id)
  2. repo.checkout(component_repo, base=target_branch, branch=naming_convention(jira_ticket_id))
  3. implement_against_ac(ticket.acceptance_criteria)
  4. tests.write_unit_and_integration()
  5. scan.security-suite()
  6. ci.run_pipeline_local()
  7. pr.open-from-template(linked_jira=jira_ticket_id, risk_class=auto, rollback_note=auto)
  8. jira.post-progress(jira_ticket_id, status="In Review", pr_link=...)
postconditions:
  - PR exists, labeled "devin-author"
  - All required CI checks pass
  - Jira transitioned to "In Review"
failure_modes:
  - On CI failure: attempt one self-heal; if still failing, comment on Jira and stop.
  - On test gap detected: do not raise PR; comment on Jira with proposed AC clarifications.

5. Tier-1 bank governance overlay

Non-negotiables to bake in before pilot:

  • Devin's sandbox runs in a VPC with egress restricted to your repos, Jira, Jenkins, package registries, and approved AI providers. No general internet.
  • Devin uses your secrets vault (CyberArk / HashiCorp). Never environment-baked credentials.
  • Every session is bound to a Jira/ServiceNow ID. No anonymous work.
  • Every Devin PR is identifiable (bot identity + label) and subject to the same SAST/SCA/SonarQube gates as human PRs, with no override.
  • Production access: read-only at most (logs, metrics, traces via observability tooling). Never write. Never deploy.
  • Audit log: session prompts, tool calls, file diffs, and PR outcomes retained for the period your audit function requires (typically 7 years for SOX-equivalent regimes).
  • Model and data residency: confirm with InfoSec which Devin model endpoints are approved and where session data is processed.

5.1 Branch-protection rules to enforce

  • Required reviewers: ≥ 2 humans for any PR authored by devin-bot.
  • Required CI checks: build, unit tests, integration tests, SonarQube quality gate, Checkmarx high-severity = 0, OWASP DC high-severity = 0.
  • Disallow merges where author and approver are both bots.
  • Signed commits required.

6. Integration with existing tooling

6.1 Jira

  • Reads tickets, posts progress as comments, transitions status.
  • Webhook on transition to Ready for Dev triggers story.implement.
  • Webhook on transition to Bug — Triaged triggers defect.triage-and-fix.
  • Devin never closes a ticket — only humans transition to Done.

6.2 Bitbucket / GitHub

  • Service account devin-bot with the minimum required permissions.
  • Branch protection enforces PR + human approvers (see §5.1).
  • PR template is mandatory; Devin populates it.
  • Devin reacts to PR comments (re-implements, adds tests) but cannot resolve a "Request Changes" review — only the human reviewer can.

6.3 Jenkins

  • Devin triggers pipelines and reads results.
  • Devin reacts to obvious failures (lint, formatting, simple test failures) and retries once.
  • Devin does not approve deployment stages.

6.4 ServiceNow

  • Devin reads incidents and posts investigation findings.
  • Change requests are still human-authored and human-approved.
  • Devin can pre-populate a CR draft; a human must submit.

8. Metrics that matter

Track from day one — without baseline you cannot defend the investment.

  • Refinement quality: % of refined stories that pass DoR without further rework.
  • PR rework rate: # of "Request Changes" rounds per Devin PR vs human PR.
  • Cycle time: ticket Ready for Dev → In Review, Devin vs human baseline.
  • Defect MTTR: bug Triaged → PR merged, Devin vs human baseline.
  • Escape rate: defects found in UAT/Prod traced to Devin PRs vs human PRs.
  • Governance incidents: count of policy/guardrail breaches (target: zero).
  • Knowledge health: stale entry count, contradictions found per quarterly review.

10. Where to start tomorrow

  1. Pick one squad with a clean repo and a supportive tech lead.
  2. Stand up the Devin sandbox in your VPC, wire it to that one repo, Jira project, and Jenkins job.
  3. Draft the first 20 Knowledge entries from §3.2 / §3.3 and review them with the squad.
  4. Implement two atomic playbooks (pr.open-from-template, jira.post-progress) and one composite (story.refine).
  5. Run story.refine against every new story for two sprints. Measure refinement quality.
  6. Only then add story.implement.
Caution: Resist the temptation to enable everything at once. The bank's risk surface is larger than the productivity upside of a fast launch.
